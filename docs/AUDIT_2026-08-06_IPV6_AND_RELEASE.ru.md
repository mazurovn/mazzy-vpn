# Аудит IPv6 egress и релиза 1.4.4

Дата: 2026-08-06

## Результат проверки

На рабочей машине активный IPv4 egress был австрийским: `151.236.9.205`,
Graz, ASN EDIS. NotebookLM достигал публичной Google redirect/login-границы.
Meta возвращал HTTP 403 от своей proxy/WAF-границы, а публичная страница
Antigravity возвращала HTTP 200. Ни один из этих ответов не доказывает
eligibility Google-аккаунта или доступность Meta для конкретной учётной записи.

Одновременно в системе существовал IPv6 default route через Wi-Fi без
подтверждённого IPv6 egress через VPN. Это был реальный leak-risk: браузер мог
предпочесть IPv6 независимо от корректного IPv4 туннеля.

## Исправление

`mazzy_vpn_ipv6_guard` устанавливается перед запуском managed tunnel service.
IPv4 явно пропускается, а IPv6 output/forward разрешён только через loopback
или активный VPN-интерфейс. При невозможности установить guard запуск VPN
завершается fail-closed. При обычном disconnect guard удаляется; после
аварийного падения он не снимается автоматически.

Guard не меняет GeoIP, cookies, регион Google-аккаунта, rollout или reputation
адреса. Поэтому он устраняет транспортную IPv6-утечку, но не гарантирует
доступность сервиса, ограниченного аккаунтом или политикой провайдера.
